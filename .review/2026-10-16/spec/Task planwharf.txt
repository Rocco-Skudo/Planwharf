# 0. MISSION

Evolve Planwharf into a professional, CLI-friendly, multi-agent project orchestration workspace.

The application must preserve its central purpose:

**Where projects dock, agents work, and progress stays anchored.**

Planwharf is not merely a terminal multiplexer or a chat interface. It coordinates AI coding agents around persistent projects, approved tasks, verified results, and resumable execution.

The new workspace should borrow useful interaction concepts from BridgeMind, especially multi-agent visibility, flexible workspace panels, terminal-style activity presentation, and easy navigation between active agents.

However, Planwharf must retain its original architecture, identity, safety guarantees, and local-first design.

The target experience:

1. The user selects a project.
2. The project-specific Orchestrator coordinates approved work.
3. Workers execute real tasks through their supported CLI/API adapters.
4. Reviewers independently verify results.
5. A configurable Supervisor monitors every participating agent and explains what is happening.
6. The user can inspect individual workers through readable terminal-style activity panels.
7. The Orchestrator produces the final project report using validated evidence.
8. A digital sailing ship continuously represents the real execution state in the application's background.
9. The user can hide the workspace dashboard and enjoy an immersive ship view without interrupting execution or notifications.
10. Skills from multiple catalogs can be selected manually or automatically and can also be generated for individual projects under controlled conditions.

This is a real implementation task, not a request for concept mockups or documentation alone.

**Do not claim success without verifying the actual running application.**

Reference:

https://www.bridgemind.ai/

- Dark, developer-oriented visual style.
- Clean typography and clear status indicators.
- Readable terminal-inspired activity panels.

# 3. CLI-FRIENDLY ACTIVITY MONITORING

This is one of the highest-priority changes.

The user wants to see what each coding agent is doing, in a terminal-like interface, without being forced to read source code or raw technical logs.

## 3.1 Two presentation modes

Implement two activity presentation levels.

### Friendly CLI — default

Show concise, understandable descriptions of observed worker activity.

Examples:

`[READ] Inspecting project configuration files`

`[WORKING] Updating the character configuration module`

`[BUILD] Compiling the project`

`[TEST] Running compatibility tests`

`[WARNING] A compilation error was detected`

`[REVIEW] Checking the recorded changes`

`[DONE] Assignment completed with validated evidence`

Descriptions must be based on actual events.

Do not fabricate activities because the worker has been running for a long time.

Do not invent compilation, file modifications, or test success.

### Technical CLI — optional

Allow the user to inspect available original command output and technical evidence.

This view may contain:

- Command execution events.
- Exit codes.
- Compiler diagnostics.
- Test results.
- File operation metadata.
- Sanitized CLI output.
- Worker identifiers.
- Provider/model identity.
- Timestamps.

Do not automatically dump complete source code or confidential data into the default interface.

Preserve original evidence for authorized debugging when available, with appropriate redaction and access boundaries.

## 3.2 Activity Translator

Build or extend a deterministic activity translation layer.

Architecture:

**Real CLI/API event → Provider-aware normalization → Activity classification → Human-readable description → UI timeline**

Prefer structured provider events when available.

Handle the existing supported adapters individually:

- Codex CLI.
- Grok CLI.
- Antigravity/Gemini CLI.
- OpenAI-compatible API connections.
- Anthropic-compatible API connections.
- Other configured adapters according to their actually verified protocols.

No assumption of uniform provider capabilities.

Implement explicit capability detection.

If an adapter cannot provide sufficiently detailed events, show the information actually available.

Use an unclassified or unknown state rather than inventing a plausible narrative.

An optional LLM-based interpretation layer can be considered later, but must not be required to display ordinary activity.

## 3.3 Worker session behavior

Each active or recorded assignment should have its own inspectable activity session.

Show:

- Role.
- Exact provider/model.
- Assigned project.
- MegaTask/SubTask identity.
- Process state.
- Most recent confirmed activity.
- Events and timestamps.
- Reported test/build outcome.
- Validated result status.
- Relevant warnings.

Support multiple concurrent workers.

Show clearly when a worker is:

- Pending.
- Running.
- Waiting.
- Reviewing.
- Failed.
- Stopped.
- Checkpointed.
- Completed.

Do not conflate process termination with validated success.

Keep the activity history inspectable after a worker finishes.

Use a bounded display strategy for long-running sessions so the UI does not become progressively slower.

## 3.4 Orchestrator responsibilities

The Orchestrator remains responsible for:

- Coordinating approved work.
- Dispatching eligible workers.
- Managing task dependencies.
- Handling review requirements.
- Producing the final project report.

The final report must be grounded in backend-validated results.

The Supervisor must not replace the Orchestrator as the author of the final execution summary.

# 4. SUPERVISOR — FOURTH OFFICIAL AI ROLE

## 4.1 Roles

Planwharf must support four distinct configurable roles:

1. `Orchestrator`
2. `Worker`
3. `Reviewer`
4. `Supervisor`

The Supervisor must become an explicit first-class model permission role.

This includes:

- Role selection in model configuration.
- Role filtering.
- Assignment validation.
- Persistent role preferences.
- Provider/model availability checks.
- Quota checks.
- Role-specific execution restrictions.
- Correct accounting for Supervisor AI usage.

Migrate existing saved configurations safely.

Older configurations with only three roles must continue to load.

Do not silently assign newly introduced Supervisor permissions to existing models.

Do not silently change existing Orchestrator, Worker, or Reviewer permissions.

## 4.2 Supervisor Core versus Supervisor AI

Separate two responsibilities.

### Supervisor Core

Always available without selecting a model.

Responsible for deterministic observation:

- Active worker processes.
- Reviewer state.
- Task state.
- Actual backend execution progress.
- Validated results.
- Errors.
- Checkpoints.
- Repeated failures.
- Stalled or potentially stalled work.
- Contradictions in recorded execution state.

No continuous LLM inference.

No new model usage required for ordinary monitoring.

### Supervisor AI

Optional model assigned the `Supervisor` role.

Responsible for reasoning over evidence:

- Explain what agents are doing.
- Analyze complex anomalies.
- Identify possible deviations from the approved plan.
- Suggest corrective actions.
- Answer the user's questions about execution.
- Interpret ambiguous or conflicting evidence.

Supervisor AI calls must be explicitly bounded and recorded.

Default automatic interpretation should remain disabled until enabled by the user.

Where automatic anomaly interpretation is permitted, trigger on meaningful events, not constant polling.

Respect the existing request budgets and quota policies.

No silent provider/model substitution.

## 4.3 Supervisor permissions

The Supervisor is advisory, not an alternative Orchestrator.

It may:

- Read authorized execution evidence.
- Inspect worker and reviewer status.
- Identify anomalies.
- Explain evidence.
- Recommend investigation.
- Recommend Pause or Stop.
- Ask the user for intervention.

It must not:

- Approve MegaTasks.
- Change approved project goals.
- Modify task permissions.
- Dispatch workers independently.
- Write project files as an advisory action.
- Run arbitrary shell commands.
- Change provider/model identity without authorization.
- Grant itself additional capabilities.
- Override backend authorization gates.

When presenting a suggested action, use the existing verified backend controls.

Pause/Stop must preserve their established confirmation and checkpoint behavior.

## 4.4 Supervisor display name

**Important personalization rule:**

`Jack Sparrow` is the owner's personal Supervisor name.

It is NOT a global product default.

It is NOT hardcoded into the application.

Every Planwharf user can choose any Supervisor name.

Rules:

- Free-text name.
- No mandatory list of names.
- Persistent after restart.
- Editable at any time.
- Whitespace-only or empty name displays exactly `Supervisor`.
- Name changes never alter technical role identity.
- Treat names as inert text, never executable instructions.
- Prevent XSS and prompt-injection-derived authority changes.
- Retain existing supported length limits unless a good reason exists to revise them.

The internal technical role always remains `supervisor`.

## 4.5 Supervisor monitoring UI

The Supervisor overview must be available inside the Orchestrator workspace.

It should show:

- All active Workers.
- All active Reviewers.
- Current task assignments.
- Real process states.
- Current and recent anomalies.
- Model/provider identity.
- Recent recorded events.
- Relevant resource/quota information when available.
- Links or controls to inspect each individual worker.
- Supervisor questions and advisory answers.

The Supervisor is the user's overview of the entire operational team.

Individual worker panels show details.

The Supervisor panel shows the big picture.

No need to duplicate every raw CLI log in the Supervisor view.

# 7. DYNAMIC SEA AND WEATHER ENGINE

The user wants the sailing ship to experience different sea conditions.

Examples:

- Calm sea.
- Light waves.
- Moderate waves.
- Rough sea.
- Storm conditions.
- Clear weather.
- Cloudy weather.
- Rain, wind, and occasional atmospheric effects.

Use lightweight local rendering where practical.

## 7.1 Weather selection modes

Implement three user-selectable modes.

### Adaptive

Sea conditions respond to a bounded estimate of the task's complexity and expected duration.

Possible signals include:

- Approved SubTask count.
- Dependency depth.
- Available complexity metadata.
- Number of participating workers.
- Task classification.
- Other reliable planning metadata.

Do not use arbitrary elapsed time as a fabricated progress estimate.

A long or complex task should allow more varied sailing conditions, not necessarily permanent storms.

Difficulty is not the same as execution failure.

Do not present decorative weather as an operational health metric.

### Random

Sea and weather conditions change using locally generated variation.

Requirements:

- Gradual transitions.
- Configurable or sensible bounded intervals.
- No constant rapid weather changes.
- No dependency on AI calls.
- No implied relationship to errors.
- Optionally deterministic per visual session to simplify reproducibility.

### Manual

Allow the user to select desired sea conditions.

This setting changes only the graphical presentation.

It must not alter actual project execution.

## 7.2 Weather safety and performance

Avoid:

- Rapid flashing.
- Excessive lightning.
- Violent camera movements.
- High-frequency roll animations.
- Distracting continuous screen-wide motion.
- Unnecessary CPU/GPU load.

Respect:

- Full animation.
- Reduced animation.
- Animation Off.
- OS reduced-motion preferences.
- Visibility/background tab throttling.

The weather engine and backend execution-state engine must be separate.

A storm is not proof of failure.

A calm sea is not proof of success.
