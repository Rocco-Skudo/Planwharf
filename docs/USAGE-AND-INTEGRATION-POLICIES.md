# Usage limits, permissions, and repository checks

In the dashboard's dedicated **Usage and permissions** section, select a provider such as ChatGPT, Grok or Gemini to view its remaining quota stop percentage, earlier remaining quota warning percentage, fallback mode/provider and **Always approve / YOLO**. Every model under the selected provider inherits these settings, including models added later. Other providers have independent settings. Changing the selector loads that provider's values into the single editor. Unsaved edits survive switching and polling; **Discard changes** restores the selected provider's saved values. Model cards contain no policy forms.

An empty stop threshold disables the custom limit. **Stop at 20% remaining** means stop starting new calls when the provider reports 20% or less of its quota left. **Warn at 30% remaining** warns earlier, while more quota is still available. A custom warning must be higher than the stop threshold. Leaving warning empty automatically warns 10 percentage points above the stop threshold, capped at 100%; a stop threshold of 100% blocks immediately and has no earlier warning. These are verified provider percentages, not assignment counts, token budgets or currency limits.

Saved earlier consumed-quota settings are read compatibly: 80% maximum consumed becomes 20% minimum remaining, and a 70% consumed warning becomes a 30% remaining warning. Original configuration and historical evidence are preserved. Earlier model-level settings are combined conservatively until a provider policy is saved: the highest remaining stop threshold, a valid earlier warning, restrictive permissions if any sibling required them, and a fallback only when all legacy routes agree on another provider. The UI marks these inherited settings for review.

The backend checks policy before a lead invocation, research dispatch, and worker scheduling. If a configured quota is unread, it blocks new calls instead of inventing a value. Without a configured stop threshold, the existing unread quota behavior remains. A quota reset clears the warning state when fresh readings fall below the threshold. Popup notices appear on state transitions and disclose a lead fallback; worker switches appear as `MODEL_USAGE_FALLBACK` timeline events with explicit provider/model identities. Editing fields survives dashboard polling until Save succeeds.

The selected lead remains recorded separately from the effective lead. Choose **Pause**, an explicit fallback provider, or **Automatic** in the fallback selector. Automatic fallback selects the first enabled, available, role-compatible model from another provider and another quota pool in catalog order. It respects the target's own quota thresholds and permissions; if no candidate qualifies, work pauses. Explicit provider fallback chains remain supported, with cycles and unavailable routes rejected. Switching happens when the stop threshold or provider exhaustion is reached, not at the warning. Approved pending worker slices follow the same policy; their recorded assignment and timeline show the replacement. Named research requests retain their exact requested model and stop at a limit rather than changing the requested identity. A configured unread quota blocks instead of guessing that the threshold has been reached.

Policies apply to future invocations. Running provider requests finish under the permissions with which they started. Quota sampling cannot enforce an exact hard spending cap during an in-flight request; parallel requests and other applications can consume quota between checks. Provider quotas are sampled through the existing adapter cache (normally 45 seconds).

Always approve / YOLO retains the existing provider bypass flags. Turning it off uses Codex's workspace write sandbox, no network access, no additional writable roots, and no automatic sandbox escalation. Source-protected research retains its existing isolated writable workspace and network-enabled sandbox, independently of YOLO. Grok uses its native `dontAsk` permission mode without `--always-approve`; this is a provider permission policy, not a Planwharf filesystem sandbox, and provider configuration still matters. Antigravity restricted unattended launches currently stop with `PERMISSION_MODE_UNSUPPORTED`; Planwharf has no interactive approval bridge for that CLI. This flag is distinct from approving a MegaTask, which remains required. Existing configurations keep their prior YOLO behavior until the user saves a policy.

These settings persist in the orchestrator state associated with each notebook and appear in project metadata exports. Keep that state with notebook backups. Policies store `minRemainingPercent`, optional `warningRemainingPercent`, and an explicit `fallbackProviderId` (null for pause, `@automatic` for automatic selection, or a configured provider ID). Policies use explicit provider IDs, assignments record exact model IDs, and quota pools retain their provider/account checks. See [external API and CLI connections](EXTERNAL-PROVIDERS.md) for adding providers and their permission and billing limits.

## GitHub and Gitea

The existing repository field accepts HTTPS GitHub or Gitea URLs, including self-hosted Gitea hosts and optional path prefixes. The notebook retains the legacy `github` field name for backward compatibility. Other non-GitHub hosts are explicitly handled as Gitea API integrations; unsupported forge APIs produce an access/schema error.

Linked projects are checked at startup and approximately every five minutes by the existing monitoring timer. Network work runs in the background so repository checks do not delay worker monitoring or deadlines. **Check repository** forces a current check. These operations refresh comparison metadata and dedicated `refs/planwharf/inspection/*` Git refs. They do not pull, merge, switch branches, push, or overwrite the working tree. Ahead, behind, diverged, unpublished branch, and access failures remain visible.

GitHub uses the existing `gh` authentication. For private Gitea repositories, configure a host-specific process environment variable, for example `PLANWHARF_GITEA_TOKEN_FORGE_EXAMPLE_COM` for `https://forge.example.com`. A host with a port includes that port in the uppercase key with punctuation replaced by underscores. Alternatively set `PLANWHARF_GITEA_ORIGIN` to the exact HTTPS origin and `PLANWHARF_GITEA_TOKEN` to its token. A generic token is never sent without a matching origin. API tokens are sent in headers; fetch credentials use scoped Git configuration in the child environment. They are not stored in notebooks or command arguments. Authenticated redirects are rejected. Public repositories need no token; existing Git credentials may still serve Git fetches.

The Gitea adapter uses the [repository branch API](https://docs.gitea.com/api/operations/repo-get-branch/), checks required metadata before comparison, and falls back to the default branch only for a missing branch (HTTP 404). A failed API check never fabricates an up-to-date result.

## Provider integration failures

Provider failures have bounded categories for CLI incompatibility, unverified response contracts, authentication, usage limits, unavailable exact model IDs, missing executables, connection failures, and unsupported permission modes. Unknown failures retain the generic execution category: an arbitrary failure is not proof that the provider changed its API.

Failed workers keep raw historical evidence and write an adjacent `.diagnostic.json` file. Failed lead calls save diagnostics with their conversation entry, and failure responses cannot dispatch embedded lead actions. Dashboard diagnostics offer **Review an issue draft**, opening the Planwharf issue form with only category, route identity, and exit code. CLI version and reproduction instructions are filled in by the user. Nothing is submitted automatically; creating a PR requires a concrete reviewed fix, not merely a runtime error.

The adapter boundary and response/result checks contain common interface changes, but arbitrary external changes cannot be guaranteed compatible. Unsupported output or missing structured results remain failures and preserve attempts for inspection.

Validation: `node engine/model-policy.test.cjs`, `node engine/gitea.test.cjs`, and `node validation/model-policy-browser.cjs`, and `node validation/worker-model-layout-browser.cjs`. The layout check covers visible standalone and embedded dashboards at 1440, 1024, and 390 pixels, with different providers selected in the dedicated settings section. These use temporary notebooks, local Git fixtures, and mocked provider launches; they perform no paid inference or personal project execution.
