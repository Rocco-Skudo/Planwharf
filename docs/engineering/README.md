# Offline engineering checks

## CI

The new pull-request-checks workflow runs on pull requests targeting main and manual dispatch, using Node 24, read-only contents permission, no persisted Git credentials, a 15-minute job limit and seven-day log artifacts. No npm install, release action, provider login, model call or Skills execution occurs. Existing release.yml is untouched. A hosted Actions result must be checked separately from the executed cloud validation reported here. The workflow becomes available to pull requests when this contribution is accepted; a run on this contribution may require maintainer approval.

Run `node scripts/engineering/ci.cjs`. It checks tracked JS/CJS/MJS syntax (excluding historical .review content), new engineering scripts during uncommitted development, working patch whitespace and, in PR CI, base-to-HEAD patch whitespace. Each required command has a 60-second timeout and individual log; a failure does not suppress later checks and causes exit 1. HOME/TEMP are disposable and the child environment is restricted to OS execution essentials. This is a reviewed test allowlist, not a general-purpose security sandbox for arbitrary future test changes.

Included pre-existing tests: engine/claim.test.cjs (12 cases, in-memory claims) and engine/attempts.test.cjs (11 cases, disposable attempt/result files and injected liveness). Both complete test files and claims.js/attempts.js/sentinel.js were inspected before inclusion. They make no provider calls. New browser.test.cjs, diagnostics.test.cjs and release.test.cjs exercise discovery/startup failure/cleanup fixtures, diagnostic privacy/confirmation and release presence/missing-file checks. See ci-test-inventory.json for every existing engine test included/excluded. All other engine tests are **not admitted pending complete transitive isolation review**, rather than silently passing or skipped failures. Root verify scripts, validation suites, historical review runners and browser acceptance are excluded: their server/provider/process and browser prerequisites have not been cleared for this CI allowlist. In particular, phase1-suite includes app windows and broad validation. No full-suite regression claim is made.

## Browsers

Select `PLANWHARF_BROWSER=edge` or `chrome`. Explicit path: `PLANWHARF_BROWSER_PATH`; existing `PLANWHARF_TEST_BROWSER` is a fallback alias. An invalid explicit path fails instead of silently selecting a different executable. Discovery checks standard Windows/macOS/Linux locations then PATH. No Firefox or Safari support claim. Browser versions come from the launched isolated instance's DevTools metadata; discovery never starts a normal user profile to probe --version.

`node scripts/engineering/browser.cjs` performs actual blank-page startup only. `node verify-browser.cjs` uses the helper for existing application checks, preserves assertions and checks console failures. Profiles are temporary; startup stderr is bounded and included in BROWSER_STARTUP_FAILED. BROWSER_MISSING and BROWSER_UNSUPPORTED are separate. Commands and DevTools connection have bounded timeouts. No sandbox-disable switch is passed. Cleanup targets the created child/process group only, or its PID tree on Windows; Windows cleanup has not been runtime-tested here.

PR #7 owns verify-layout.cjs, verify-workspace-browser.cjs and verify-ship-browser.cjs. integration/pr7-browser.patch is an **unapplied proposal against exact head 7b70ea6**, with successful patch-application and syntax checks only. It reuses existing CDP assertions and adds shared launch/discovery/cleanup. Apply after the shared helper is accepted, using `git apply --check docs/engineering/integration/pr7-browser.patch` against that head before applying. No PR-owned source file was edited here. Existing other harnesses still need migration; do not claim repository-wide portability. Neither actual Edge nor Chrome is installed/discoverable in this cloud environment; fixture success is not browser success.

## Diagnostics

`node scripts/engineering/diagnostics.cjs` prints a readable preview and, only in an interactive terminal after typing EXPORT, creates planwharf-support.json with exclusive creation and mode 0600. Noninteractive invocation refuses export. No upload, telemetry or automatic collection. API generate/preview/exportPreview supports callers supplying only known categorical metadata. Adapters/versions are supplied explicitly; no provider executable is probed. Unknown values become unknown, raw errors become categories, arbitrary fields are dropped. Exact-preview hash confirmation and full output-shape revalidation precede export. It does not read notebook contents, raw logs, environment dumps, account records or private source. Preview users must still review metadata before sharing.

Integration boundary: UI may pass explicit category/availability/test metadata then render preview and ask for confirmation. Do not wire into Orchestrator or PR-owned settings UI until coordinated. Adapter availability is not authentication/access verification. Browser version and OS release are omitted from the bundle initially; Node/platform/architecture and safe supplied app/adapter semvers are supported. No application version is invented when unavailable.

## Release and accessibility

`node scripts/engineering/release-smoke.cjs [ZIP]` checks launcher presence, Windows MZ header and shell/Windows Node invocation; optionally verifies ZIP required files, safe names, size bound and manifest hashes. It starts an isolated Node CLI status check and backend HTTP server with empty models and dispatch/inference forbidden. The ZIP checker uses Python standard library, matching existing packaging; it does not extract or execute an untrusted ZIP. The app startup uses the inspected source directory, not a supplied ZIP.

`node scripts/engineering/package-smoke.cjs` invokes existing packaging into a disposable directory with fixture version v0.0.0, verifies the generated ZIP and manifest, runs status/backend from that packaged directory and rejects an incomplete ZIP. No source version/tag or release is changed. Node is required; shell/cmd currently defer missing-Node handling to the OS, while C# launcher contains explicit detection. Windows executable packaging is static MZ/presence validation only. Windows executable execution, macOS shell execution, GUI startup, real worker cleanup and missing-Node UI are unverified. Linux Node CLI and HTTP startup were actually executed; shell launcher runtime was not.

Accessibility source inventory commands and prioritized findings are in ACCESSIBILITY.md. The inventory is informational source evidence, not a DOM fixture, browser pass or conformance test.
